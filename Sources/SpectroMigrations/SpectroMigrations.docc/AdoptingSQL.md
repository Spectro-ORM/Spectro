# Adopting existing SQL migrations

Bundle existing SQL files unchanged and register new Swift declarations alongside them.

## Overview

### Preserve the ledger's identity

SQL and Swift migrations share the `schema_migrations` ledger, full migration ID, lexical ordering, session lock, and transactional engine. You do not need to rewrite the database or convert historical files to adopt the DSL.

Keep existing SQL filenames, contents, and IDs. An applied file named `1791129599_create_legacy_labels.sql` is identified by `1791129599_create_legacy_labels`, including the name. Translating it into a Swift declaration with a new ID would describe another migration.

### Include SQL as target resources

Copy the existing files to `Sources/MyAppMigrations/LegacySQL`. Add the directory to the executable target:

```swift
.executableTarget(
    name: "MyAppMigrations",
    dependencies: [.product(name: "SpectroMigrations", package: "Spectro")],
    resources: [.copy("LegacySQL")]
)
```

Retain the existing section markers:

```sql
-- migrate:up
CREATE TABLE legacy_labels (name TEXT NOT NULL);

-- migrate:down
DROP TABLE legacy_labels;
```

Legacy SQL files with an empty down section retain their existing no-op rollback behavior. New typed declarations express irreversibility explicitly.

### Assemble the registry

```swift
import SpectroMigrations

let migrations = MigrationRegistry {
    SQLMigrations(bundle: .module, directory: "LegacySQL")
    CreateUsers()
    CreateIssues()
}
```

`Bundle.module` is generated by SwiftPM for a target with resources. ``SQLMigrations`` resolves the directory from that bundle, independently of the process's working directory. An absent resource directory fails planning; it is never treated as empty history.

``MigrationRegistry/sources()`` compiles the captured Swift plans and validates the combined catalog without connecting to PostgreSQL. Duplicate full IDs fail even when they come from different source formats. Full IDs sort lexically, so different names with the same timestamp remain distinct entries. Source registration order does not determine execution order.

### Check the complete artifact

```sh
spectro migrate plan
spectro migrate status
```

Planning checks bundled history offline. Status connects to the target database and reports applied IDs missing from the executable. Keep every applied migration in future artifacts: rollback will not skip a missing recent ID to choose an older one.

Copy the resource bundles alongside the release executable when deploying. See <doc:Deployment> for build and runtime requirements.
